# 架构说明

## 设计目标

通信层和业务层必须在没有 WinForms 的环境中直接运行，为二期命令行模式、脚本执行和自动化测试保留复用能力。界面只负责输入、调用、事件订阅和控件刷新。

## 依赖方向

```text
ModbusHelper.WinForms
        |
        v
ModbusHelper.Business
        |
        v
ModbusHelper.Communication
        |
        v
ModbusHelper.Core
```

项目引用必须遵守以下规则：

- `Core` 不引用其他项目，不依赖 NModbus 或 UI 类型。
- `Communication` 只引用 `Core`、NModbus 和 .NET 基础库。
- `Business` 只引用 `Core` 和 `Communication`，不得直接调用 NModbus。
- `WinForms` 只引用 `Business`，通过业务层事件或回调获得状态，不直接调用通信层。
- `Program` 只做模式选择和宿主启动，依赖装配集中在 `AppCompositionRoot`。

## 核心边界

### 通信层

`ModbusService` 是 UI 无关的语义化入口。它负责参数校验、连接建立、NModbus 调用、原始帧记录、异常转换和释放，不负责轮询调度或界面通知。

每个连接拥有唯一的串行读写上下文。主站实例、串口和网络流均按 `IDisposable` 管理，并由连接所有者统一释放。

### 业务层

业务层负责连接状态、多个轮询任务、点位解析、日志、统计和趋势数据。后台轮询只写线程安全缓冲区，不接触控件。

业务层通过事件、回调或 `IProgress<T>` 发送状态。CLI 或脚本宿主可以直接订阅同一组事件，不需要 WinForms。

### 界面层

界面层不包含 Modbus 读写逻辑和轮询循环。趋势图由一个 200 毫秒 WinForms 定时器统一批量刷新，禁止后台线程逐点调用 `Invoke` 或 `BeginInvoke`。

## 线程与资源约束

- 同一个 `IModbusMaster` 的调用必须串行化。
- 不同连接各自持有独立主站和串行队列，可以并行。
- 趋势缓冲区采用固定容量，默认每条曲线保留 5000 个点。
- 串口和 Socket 在正常断开时主动释放，并在窗体关闭和对象释放时兜底。
- 所有释放路径必须具备 `_disposed` 防重入保护。

## 验证方式

- 构建整个解决方案。
- 运行 `scripts/verify-layer-boundaries.ps1` 检查底层项目是否出现 UI 命名空间或控件类型。
- 使用 Modbus TCP 自环完成首轮集成测试，再使用 com0com 等虚拟串口覆盖 RTU。
- 对参数边界、异常码、断线、重复释放、轮询串行和趋势容量进行专项验证。
